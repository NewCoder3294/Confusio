# Mendacity Defensive — Foundry Ontology Spec

**Audience:** Nicolas, in Foundry Ontology Manager.
**Purpose:** click-through reference for building the two defensive object types.
Property names here bind exactly to `defensive/persistence/foundry_writer.py` and the
Workshop bindings in `palantir/defensive/workshop.md`. If anything here disagrees
with what `foundry_writer.py` emits, the writer wins — update this doc to match.

## Build order

1. Object types: `InboundArtifact` → `InboundDetection` (Artifact first; Detection FK-references it).
2. Link type after both object types are saved.
3. Actions are auto-generated by Foundry when you enable Edits on each type. Add PK
   params manually after generation per the convention below.

---

## 1. Object types

### 1.1 `InboundArtifact`

One row per verify call. The top-level record that collects the operator's submission
and the composite verdict.

**Setup:**
- API name: `InboundArtifact`
- Display name: `Inbound Artifact`
- Compass folder: `Mendacity/Defensive`
- Backing dataset: `mendacity-inboundartifact`
- Configure without datasource: **yes**
- Edits-Enabled: **yes** (this auto-generates the Create / Edit / Delete actions)
- Primary key: `artifact_id` (string) — set as Title key

**Properties:**

| Property (snake_case) | Display name | Type | Action param (camelCase) | How param is added | Notes |
|---|---|---|---|---|---|
| `artifact_id` | Artifact ID | string | `artifactId` | **Manual** — PK is not auto-included | UUID; Title key |
| `sha256` | SHA-256 | string | `sha256` | Auto | Indexed for dedup; full hex string |
| `file_name` | File Name | string | `fileName` | Auto | Nullable (bot path omits the original filename) |
| `mime` | MIME Type | string | `mime` | Auto | One of: `image/jpeg`, `image/png`, `image/webp` |
| `bytes` | Bytes | integer | `bytes` | Auto | Raw file size in bytes |
| `submitted_at` | Submitted At | timestamp | `submittedAt` | Auto | API receive time; ISO-8601 with timezone |
| `submitted_via` | Submitted Via | string | `submittedVia` | Auto | One of: `verify_tab`, `telegram_bot`, `api_direct` |
| `operator` | Operator | string | `operator` | Auto | Mapped operator identity string |
| `verdict_level` | Verdict Level | string | `verdictLevel` | Auto | One of: `AUTHENTIC`, `SUSPECT`, `SYNTHETIC` |
| `verdict_confidence` | Verdict Confidence | double | `verdictConfidence` | Auto | 0.0 – 1.0; strength of evidence backing the verdict |
| `verdict_summary` | Verdict Summary | string | `verdictSummary` | Auto | One-line operator-readable conclusion |
| `thumbnail_uri` | Thumbnail URI | string | `thumbnailUri` | Auto | Nullable; Foundry media-set URI for 256 px thumbnail |

**Manual PK param step (after auto-generation):**

1. Open the auto-generated `Create Inbound Artifact` action.
2. Click `+ Add parameter`.
3. Name: `artifactId`, Type: `String`, Required: yes.
4. In the action rule, find the `artifact_id` property binding and change its source from
   "unbound" to the new `artifactId` parameter.
5. Repeat steps 2–4 for the `Edit Inbound Artifact` action (the PK param is what
   Foundry uses to locate the row to edit).

### 1.2 `InboundDetection`

N rows per `InboundArtifact` — one per detector that ran. Never merged into the parent
artifact; the per-row granularity is what makes the Workshop detail view and future
bulk queries useful.

**Setup:**
- API name: `InboundDetection`
- Display name: `Inbound Detection`
- Compass folder: `Mendacity/Defensive`
- Backing dataset: `mendacity-inbounddetection`
- Configure without datasource: **yes**
- Edits-Enabled: **yes**
- Primary key: `detection_id` (string) — set as Title key

**Properties:**

| Property (snake_case) | Display name | Type | Action param (camelCase) | How param is added | Notes |
|---|---|---|---|---|---|
| `detection_id` | Detection ID | string | `detectionId` | **Manual** — PK manual add | UUID generated by the writer per-signal |
| `artifact_id` | Artifact ID | string | `artifactId` | Auto | FK → `InboundArtifact.artifact_id` |
| `detector_name` | Detector Name | string | `detectorName` | Auto | One of: `c2pa`, `synthid`, `titan`, `ai_classifier`, `exif`, `ela`, `phash` |
| `severity` | Severity | string | `severity` | Auto | One of: `pass`, `warn`, `fail`, `n/a` |
| `score` | Score | double | `score` | Auto | Nullable; detector-native probability or magnitude |
| `evidence` | Evidence | string | `evidence` | Auto | One-line free text from the detector |
| `latency_ms` | Latency (ms) | integer | `latencyMs` | Auto | Per-detector wall-clock elapsed in milliseconds |
| `ran_at` | Ran At | timestamp | `ranAt` | Auto | Timestamp when the detector run was captured; matches `InboundArtifact.submitted_at` for v1 |

**Manual PK param step (after auto-generation):**

Same procedure as for `InboundArtifact`:
1. Open `Create Inbound Detection` → `+ Add parameter` → name `detectionId`, type String, required.
2. Bind the `detection_id` property to the `detectionId` param in the rule.
3. Repeat for `Edit Inbound Detection`.

## 2. Link type

Build after both object types are saved and confirmed.

| Field | Value |
|---|---|
| API name | `InboundArtifactToDetections` |
| Display name | `detections` (on the `InboundArtifact` side); `artifact` (on `InboundDetection` side) |
| From | `InboundArtifact` |
| To | `InboundDetection` |
| Cardinality | One-to-many (one artifact → N detections) |
| Join key | `InboundArtifact.artifact_id` = `InboundDetection.artifact_id` |

In Workshop the link lets you render the child detection rows directly in the artifact
detail view without a manual filter.

## 3. Actions

All six actions are **auto-generated** when Edits-Enabled is turned on. The table below
shows the SDK kebab-case names that `defensive/persistence/foundry_writer.py` calls.

| Foundry display name | SDK API name | Used by writer? |
|---|---|---|
| Create Inbound Artifact | `create-inbound-artifact` | fallback (upsert) |
| Edit Inbound Artifact | `edit-inbound-artifact` | primary (upsert try) |
| Delete Inbound Artifact | `delete-inbound-artifact` | not used in v1 |
| Create Inbound Detection | `create-inbound-detection` | fallback (upsert) |
| Edit Inbound Detection | `edit-inbound-detection` | primary (upsert try) |
| Delete Inbound Detection | `delete-inbound-detection` | not used in v1 |

**Upsert pattern:** the writer tries `edit-<type>` first; on failure falls back to
`create-<type>`. This mirrors the pattern in `palantir/aip/result_ingester.py`. Because
`detection_id` is a new UUID per verify call, create will almost always be the live
path; edit is defensive in case of a retried request.

## 4. Parameter naming conventions (verified empirically)

These conventions are identical to the offensive side (`palantir/ontology.md` and
`result_ingester.py`):

- Foundry **auto-camelCases** every property-backed param (e.g. `verdict_level` →
  `verdictLevel`, `submitted_at` → `submittedAt`).
- The PK is **not** auto-included; it must be added by hand.
- Manually-added params keep the literal text typed — type them in camelCase (e.g.
  `artifactId`, `detectionId`) to match what `foundry_writer.py` sends.
- All non-PK params are camelCase regardless of how the underlying property is named.
- Foundry marks every parameter required by default; the writer passes empty string /
  null for optional fields rather than omitting them.

## 5. What is intentionally not in this ontology

- **Cross-linking to `Mission` or `Artifact`** — deferred to post-v1; the "did this
  inbound image trace back to one of our outbound campaigns?" query requires a separate
  link type and a phash/sha256 join strategy. See the spec's non-goals.
- **Operator as an object type** — v1 treats `operator` as a free string on both
  `InboundArtifact` and `InboundDetection`. v2 lifts to a linked `Operator` type.
- **Binary image storage** — Foundry media-sets handle this; `thumbnail_uri` records
  the Foundry URI once the thumbnail is pushed. The bytes themselves are never stored
  in the object properties.
- **Batch ingest** — no `BatchVerify` type for v1.

## 6. Smoke check after build

1. In Ontology Manager, confirm both types are saved and `Edits-Enabled`.
2. From the Actions panel, confirm six auto-generated actions appear with the SDK names
   above.
3. Open `Create Inbound Artifact`, confirm `artifactId` param exists and binds to
   `artifact_id`.
4. Open `Create Inbound Detection`, confirm `detectionId` param exists and binds to
   `detection_id`.
5. Run `palantir/bridge/foundry_bridge.py` smoke-test mode and confirm a single
   `InboundArtifact` row lands in the backing dataset.
6. Confirm the `InboundArtifactToDetections` link resolves when you open one artifact
   row in Workshop.
